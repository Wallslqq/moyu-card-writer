# MVU：讨论变化规则

## 一、输入与职责

这是“变量结构”和“开局值”之后的一步。网页自动带入当前`schema.js`、`initvar.yaml`、已有开局设计和规则设计，普通问答也能读取，不要求作者重新粘贴。

结构脚本提供字段类型、动态集合项目结构、完整枚举和约束；开局值提供实际起点。已确认的设计与本轮创意说明更新意图，没有旧版设计标签不影响使用正式文件。首次创作缺少结构或开局文件时，用可见页签名说明应先完成哪一份；已有文件修复不强迫重走设计流程。

本轮只回答：“游玩中依据什么事实更新现有变量，什么情况下保持不变？”不把人设、世界观再写一遍。

## 二、选择必要规则

逐个字段判断：

1. 是否允许由模型更新？`_`开头或已确认仅由代码维护的字段不进入规则。
2. 字段名和结构是否已能表达普通更新？作者没有特殊条件时，可不额外写规则。
3. 触发时机、知情边界、变化幅度或增删方式有没有真实歧义？只处理实际需要。
4. 多个字段是否遵循同一语义？可以合并，不重复堆积。

没有专门规则不等于变量失效。不要为“完整”添加空泛check。

## 三、逐轮确认更新行为

每轮先回答作者，再只问一个重要问题；已说明的事实不换词追问。

按当前字段需要确定：正文中什么事实触发更新、什么情况下保持、谁必须知情、怎样增减或替换、集合何时增删、哪些字段必须同步变化。范围与固定选项沿用结构；单次幅度或阶段切换只采用作者确认的规则。

`check`是给剧情模型阅读的自然语言判断，不是要编译成结构脚本的代码。只写能区分允许更新与保持不变的条件，不写“根据剧情合理更新”这样的空话，也不穷举所有未来事件。

若需要新增字段、改变类型或权限，先在“变量结构”确认调整，再补对应开局值；只是起点不对则改“开局值”。

## 四、确认与输出

第一次整理用`<MVU变量规则设计终稿_待确认>`，作者确认后输出一个text代码块：

```text
<MVU变量规则设计终稿>
规则对象：变量或同规则字段组
对应字段：结构中的真实路径
触发事实：允许改变所必需的事实
保持条件：仅在需要时出现
知情边界：仅在需要时出现
变化方式：替换／增减／插入／删除／移动
变化幅度：仅在作者要求时出现
集合操作：仅在集合需要专门规则时出现
复合一致性：仅在实际需要时出现
无需专门规则：已确认无需特殊限制的可更新字段
</MVU变量规则设计终稿>
```

只保留实际需要的栏目；没有特殊规则时明确“需要正式规则：无”。不夹带初始数据、代码、旧稿或被否决规则。

网页等待作者确认保存规则设计。随后在“变化规则”提出生成文件，确认写入`变量更新规则.yaml`后去“交叉检查”；不用返回末尾补生成结构，也不会后台自动生成文件。
